# HEAVIX Backup Encryption Design

**Status:** Implemented in the PR archive workflow source; exact-head CI and owner key-custody verification are pending.  
**Scope:** PR #188, Preview-only backup artifacts.  
**Production:** Explicitly excluded.  
**Cost constraint:** No paid service or permanent server.

## Security objective

Database dumps and source-history archives must be encrypted on the ephemeral GitHub Actions runner before any object is uploaded to Backblaze B2. Bucket-side encryption is defense in depth, not a replacement for client-side encryption.

## Selected format and tool

Use the upstream `age` file-encryption format and CLI, pinned to version `1.2.1` for the first implementation. The upstream project documents public recipients, private identities, authenticated encrypted files, and non-interactive CLI operation. Do not use passphrase mode in CI.

- Public recipient: repository variable `HEAVIX_B2_AGE_RECIPIENT`. It is not secret.
- Private identity: generated by the owner on a trusted offline machine and retained outside GitHub, B2, the repository, and this chat.
- The GitHub Actions runner receives only the public recipient. It must never receive the private identity or a decryption passphrase.
- A separate offline restore operator uses the private identity to decrypt downloaded objects.

Upstream references:
- https://github.com/FiloSottile/age
- https://github.com/FiloSottile/age/blob/main/doc/age.1.ronn

## Key generation and custody

1. On a trusted offline machine, create a private working directory and restrictive file permissions:
   ```sh
   umask 077
   age-keygen -o heavix-backup-identity.txt
   age-keygen -y heavix-backup-identity.txt > heavix-backup-recipient.txt
   ```
2. Keep `heavix-backup-identity.txt` offline. Inspect and copy only the public value from `heavix-backup-recipient.txt`.
3. Store only the public recipient in the GitHub repository variable `HEAVIX_B2_AGE_RECIPIENT`.
4. Store the private identity in at least two controlled offline recovery locations, protected by the owner's existing secure custody process. Do not store both copies in the same cloud account or same physical location.
5. Record the identity fingerprint and custodian in the private operational inventory, never the private key itself.
6. Test decryption from a disposable fixture before the first real archive. Do not upload real backups until the restore operator confirms possession and successful recovery.
7. Key rotation must add the new public recipient before switching the workflow. During transition, encrypt to both old and new recipients. Retain the old identity until every archive encrypted only to it has passed retention expiry and restore acceptance.

No key generation, key upload, secret creation, bucket creation, database contact, or real archive has been performed by this PR execution.

## Archive transformation

The workflow must:

1. Produce the Main and Store PostgreSQL custom-format dumps and the two repository bundles/source snapshots in a private ephemeral runner directory with restrictive permissions.
2. Produce a non-sensitive manifest containing repository commit SHAs, run ID, timestamps, format labels, and original plaintext byte sizes. It must not contain database URLs, credentials, customer rows, or secret values.
3. Encrypt each payload independently to the public recipient:
   - `main.dump.age`
   - `store.dump.age`
   - `heavix-source.bundle.age`
   - `heavix-source.tar.gz.age`
   - `heavix-legacy.bundle.age`
   - `heavix-legacy.tar.gz.age`
4. Remove plaintext staging payloads immediately after successful encryption. The ephemeral runner is then discarded; do not claim secure erasure on hosted runner storage.
5. Generate `SHA256SUMS` over encrypted payloads and the non-sensitive manifest.
6. Upload only encrypted payloads, `manifest.json`, and `SHA256SUMS`. The upload allowlist must reject every plaintext dump, bundle, and tarball filename.
7. Download each uploaded object to the same ephemeral runner and compare its SHA-256 with the local digest. The checksum manifest itself is checked against a separately computed local digest.
8. Never print DSNs, B2 keys, private identities, decrypted payload contents, or customer data.

The manifest and checksum file may remain plaintext because they contain only public operational metadata and ciphertext hashes. If that metadata later becomes sensitive, encrypt a second copy while retaining the minimal checksum index required for ciphertext verification.

## Restore acceptance

A backup is not considered recoverable until all of the following pass:

1. Download encrypted artifacts from the dedicated private backup bucket.
2. Verify SHA-256 checksums before decryption.
3. Decrypt using the offline private identity into a newly provisioned isolated PostgreSQL 17 restore environment.
4. Run `pg_restore --list`, then perform actual restores of Main and Store into separate disposable databases.
5. Verify migration history, critical row counts, constraints, indexes, extension availability, and application-level smoke checks.
6. Record restore duration, exact source commit/run ID, key fingerprint, and result without recording the private key or database URLs.

Never restore over Preview or Production during a rehearsal.

## Required fail-closed conditions

The workflow must not proceed unless:

- Both source DB destinations have been independently fingerprinted as the intended App Preview and Store Preview resources.
- The credentials are dedicated, least-privilege, and read-only for the required objects.
- The public age recipient is present and syntactically valid.
- The dedicated private bucket `heavix-db-backups` exists.
- The B2 application key is scoped only to that bucket and required object operations.
- Retention, data cap, and expected cost are documented and remain within the zero-cost constraint.
- Offline private-key custody and a disposable restore target are confirmed.
- CI proves encryption/decryption round-trip and rejects modified ciphertext.
- The upload allowlist contains only encrypted payloads and non-sensitive metadata.

Repository variables are attestations, not evidence. They must not be set until the underlying checks have been independently completed.

## Explicit exclusions

- No Production database or Production credentials.
- No B2 writes or bucket creation as part of design validation.
- No private key or decryption secret in GitHub Actions.
- No public bucket access.
- No claim that local `public/uploads` media, DNS, Cloudflare settings, provider configuration, or secret-manager state are included.
- No paid backup service, VPS, or permanent Docker host.
