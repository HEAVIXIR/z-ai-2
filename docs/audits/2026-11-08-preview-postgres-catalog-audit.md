## Interpretation and limitations

This live catalog pass was followed by normalized comparisons against the checked-in
Prisma schemas at `a1d6fb2ac28421056a87fbb5feafdc0121efc65a`. The results below strengthen
the parity evidence, while retaining explicit limits on the remaining edge cases.
Earlier checks on this branch established:

- Main: 120/120 Prisma models have corresponding live tables; zero column-name,
  scalar-type, or nullability differences.
- Store: 34/34 Prisma models have corresponding live tables; zero column-name,
  scalar-type, or nullability differences.

The additional normalized comparisons found:

- Database defaults: 355 Main and 93 Store schema-declared literal/server defaults were
  compared to live catalog values; zero mismatches. The remaining 116 Main and 32 Store
  `cuid()` defaults are Prisma Client-side ID generators, not PostgreSQL column defaults,
  and are intentionally excluded from database-default comparison.
- Index signatures: all 288 Main and 83 Store Prisma-declared primary/unique/ordinary
  index signatures matched live indexes by table, ordered column list, uniqueness, and
  primary-key role. The live inventory has one additional Main index and three additional
  Store indexes: migration bookkeeping and the Store implicit many-to-many join table
  account for the extra inventory. PostgreSQL's 63-byte identifier truncation explains
  why two long generated index names differ textually from Prisma's untruncated expected
  names; their table/column/uniqueness signatures match.
- Foreign keys: all 124 Main and 34 Store explicit Prisma relation definitions matched
  live foreign keys by source columns, referenced table/columns, and ON DELETE/ON UPDATE
  actions. Store has two additional live FKs for the implicit many-to-many join table.
  Every observed FK is validated.

Additional PostgreSQL catalog checks found zero expression indexes, zero partial indexes,
zero INCLUDE indexes, zero non-default collations, and zero non-default operator classes
in either Preview database. All live indexes are ordinary B-tree signatures matching the
Prisma-declared table/column/uniqueness structures in the normalized comparison.

These are normalized structural comparisons, not proof of migration-history equivalence
or every unusual native annotation. The 148 `cuid()` defaults are generated by Prisma
Client rather than PostgreSQL and were correctly excluded from DB-default parity.
Migration-history equivalence remains separate from live catalog parity. Release approval
still requires the independent database-destination and backup gates.

## Follow-up effective-role privilege audit — 2026-11-09

A separate read-only PostgreSQL role-catalog audit was run against both dedicated
Preview resources. It used SELECT-only queries against `pg_roles`,
`pg_auth_members`, `pg_default_acl`, and `information_schema`; no application
rows were read.

| Effective role property | Main Preview | Store Preview |
|---|---:|---:|
| Current role | `prisma_application` | `prisma_application` |
| Superuser | false | false |
| Create role / create DB | false / false | false / false |
| Replication attribute | **true** | **true** |
| Bypass RLS | false | false |
| Inherited role memberships | `pg_read_all_data`, `pg_write_all_data` | `pg_read_all_data`, `pg_write_all_data` |
| Membership INHERIT / SET | true / true for both | true / true for both |
| Role-level config | `idle_session_timeout=300000` | `idle_session_timeout=300000` |
| Public tables with effective INSERT/UPDATE/DELETE | 121/121 | 36/36 |

The direct `information_schema.table_privileges` count for explicit grants to
`prisma_application` is zero in both databases; this does **not** mean the role
is read-only. Effective DML is inherited from the predefined PostgreSQL role
`pg_write_all_data`, and the role also has the `REPLICATION` attribute.
The role is therefore unsuitable as a least-privilege read-only proof identity.

This audit does not establish that GitHub Actions secrets or Cloudflare Worker
bindings use the same role; their secret values were not read. The result applies
to the Prisma SQL tool's current role on the selected Preview resources.

### Required remediation and gate

Before a read-only runtime proof, provision dedicated Preview-only roles with
no `pg_write_all_data` membership, no replication attribute, no inherited

connection string in the protected GitHub Environment. Separately review
whether the existing application role needs `pg_write_all_data` and
`REPLICATION`; do not revoke either privilege without a reviewed application
impact assessment.

No role attributes, memberships, grants, database settings, connection strings,

**NO-GO** pending least-privilege credentials, scoped runtime proof, independent
