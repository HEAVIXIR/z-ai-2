#### 3b. `getUserRoleWithFallback()` consults legacy `User.role` ONLY on `EMPTY`

**File:** `src/lib/authorization/role-shim.ts`
**Lines:** 57-99

```ts
export async function getUserRoleWithFallback(
  userId: string | null | undefined,
  user?: { role?: string | null } | null,
): Promise<string> {
  const { role: canonical, status } = await getUserPrimaryRoleWithStatus(userId);

  // Rule 1: canonical non-BUYER → canonical wins.
  if (canonical !== "BUYER") return canonical;                     // L65

  // Rule 4: DB_ERROR → return "BUYER" WITHOUT consulting legacy.
  if (status === "DB_ERROR") return "BUYER";                       // L69 ← CRITICAL

  // Rule 2: FOUND + BUYER → canonical wins.
  if (status === "FOUND") return "BUYER";                          // L74

  // Rule 3: status === "EMPTY" — consult legacy User.role.
  let legacyRole: string | null | undefined;                      // L77
  if (user && typeof user === "object" && "role" in user) {
    legacyRole = user.role;                                       // L79 — uses pre-fetched user.role
  } else if (userId) {
    try {
      const u = await db.user.findUnique({                        // L82 — queries legacy column
        where: { id: userId },
        select: { role: true },
      });
      legacyRole = u?.role ?? null;
    } catch (err) {
      console.error("[role-shim] legacy User.role lookup failed:", err);
      return "BUYER";                                              // L91 — fail-closed
    }
  }

  const r = String(legacyRole ?? "").toUpperCase();
  return r && r !== "BUYER" ? r : "BUYER";                        // L98
}
```

**Decision matrix:**

| Status | Canonical | Action | Result |
|---|---|---|---|
| (any) | ADMIN/SELLER/MODERATOR/SUPPORT | Rule 1 — return canonical | canonical wins |
| `FOUND` | BUYER | Rule 2 — return `"BUYER"` | canonical wins (do NOT consult legacy) |
| `EMPTY` | BUYER (default) | Rule 3 — consult legacy | legacy value (or `"BUYER"` if null) |
| `DB_ERROR` | BUYER (default) | Rule 4 — return `"BUYER"` | **DO NOT consult legacy** ✅ |

The critical security property: when `status === "DB_ERROR"`, the shim returns `"BUYER"` and skips the legacy `User.role` lookup entirely. If the legacy DB read were attempted during an outage, it would either throw (caught, return BUYER) or worse, potentially read a stale cached value. The current implementation avoids both by short-circuiting on `DB_ERROR`. ✅

This is verified by `tests/security/rbac-phase-b.test.ts:195-208` ("Test 5: DB-error → {BUYER, DB_ERROR}; shim returns BUYER (NOT legacy)"), which explicitly mocks `findMany` to reject and asserts the shim returns `"BUYER"` not `"SELLER"` even when the legacy `user.role === "SELLER"`.

## §2. Authorization Separation Verdict

### ✅ CLEAN — no authorization path imports the shim

The Phase B design separates the world into two non-overlapping sets of consumers:

1. **Authorization paths** (decide "is this allowed?"):
   - `src/lib/authorization/index.ts` — `can`, `canAny`, `canAll`, `requirePermission`, `requireAnyPermission`, `requireAllPermissions`, `isAdmin`, `canAccessResource`, `canBulkAction`, `canExport`, `hasRole`
   - `src/lib/rbac-legacy.ts` — `getUserPermissions`, `ForbiddenError`
   - `src/lib/rbac.ts` — pure re-export shim for backward import compatibility
   - `src/lib/admin-guard.ts` — `adminGuard`, `requireAdmin`, `requireOwnership`, `authorizeAdmin`

2. **Display/serialization paths** (decide "what role string should I show?"):
   - `src/lib/authorization/role-shim.ts` — `getUserRoleWithFallback`
   - `src/lib/authorization/user-roles.ts` — `getUserPrimaryRole`, `getUserPrimaryRoleWithStatus`, `getUserRoleKeys`, `getUserRoleLabels`
   - Consumers: `src/app/dashboard/page.tsx`, `src/app/admin/sellers/[id]/page.tsx`

The shim file is the **only** module that consults the legacy `User.role` column for fallback purposes. None of the four authorization-path modules imports it (Invariant 5). The authorization chain (`can()` → `getUserPermissions()` → UserRole graph) does NOT touch `User.role` (Invariant 6).

This separation means:
- A DB outage affecting `User` reads (legacy column) cannot affect authorization decisions (which read UserRole → Role → RolePermission → Permission).
- Conversely, a partial DB issue affecting only UserRole reads will cause `getUserPermissions()` to return `[]` → `can()` returns `false` → request denied (fail-closed). The role shim's `EMPTY`/`DB_ERROR` distinction only impacts DISPLAY (what role badge to show), not authorization.
- There is no path where `User.role` could escalate authorization. Even if an attacker managed to set `User.role='ADMIN'` directly on a user with no UserRole row, the authorization chain (`can()`) would still query UserRole and return `[]` → deny.

**Verdict:** The authorization-separation invariant (REVISION-7) is fully satisfied. ✅

## §5. Security Findings

### 5a. No critical findings

The implementation satisfies all 10 invariants. No authorization path consults the legacy `User.role` column. The shim is properly isolated to display paths only.

### 5b. Informational notes (not security defects)

1. **Phase B intentional dual-read window:** During Phase B, both `User.role` (legacy) and `UserRole` (canonical) coexist. The dual-write invariant (Invariant 1) keeps them consistent. The shim's `EMPTY` case handles un-backfilled users (whose `User.role` is set but who lack UserRole rows) by falling back to legacy for DISPLAY only — authorization is unaffected. This is intentional and documented.

2. **Client component reads of `user.role`:** Two client components (`users-section.tsx`, `user-detail-drawer.tsx`) read `user.role` directly (Invariant 9). They cannot use the async shim. The dual-write keeps `user.role` consistent with UserRole during Phase B. Phase D cutover (dropping the `User.role` column) will require migrating these to receive the shim-resolved role via props. Both files have explicit comments documenting this future migration.

3. **Audit log payload still uses legacy `role` field:** The audit log records `existing.role` and `updated.role` (the legacy column) in its before/after payloads (e.g. `src/app/api/admin/users/[id]/route.ts:279-280`). Per REVISION-6 comment (lines 268-272), this is intentional during Phase B because the dual-write keeps the legacy column in sync. Phase D will switch the audit payload to the canonical UserRole key.

4. **`requireOwnership` uses `isAdmin` for owner check:** `src/lib/admin-guard.ts:113-121` — `requireOwnership(userId, resourceOwnerId)` returns true if `userId === resourceOwnerId` OR `isAdmin(userId)` is true. This means an admin can access any resource regardless of ownership, which is the intended behavior (admins have global access). The check uses RBAC `isAdmin`, not legacy `User.role`. ✅

5. **`hasRole` legacy shim:** `src/lib/authorization/index.ts:356-367` — the `hasRole(userId, roles)` function translates legacy role keys (`ADMIN`, `SELLER`, etc.) into canonical permission keys (`admin.access`, `seller.access`, etc.) via `ROLE_PERMISSION_MAP` and delegates to `can()`. This is itself an authorization-path function, but it does NOT consult `User.role` — it routes through `can()` which uses the RBAC chain. Documented as a migration shim to be removed once all callers migrate to `can(userId, 'admin.access')` style.

### 5c. No authorization-path `User.role` consultation anywhere

Grep-verified: the authorization modules (`src/lib/authorization/index.ts`, `src/lib/rbac.ts`, `src/lib/rbac-legacy.ts`, `src/lib/admin-guard.ts`) contain ZERO queries of the `User.role` column. The only reads of `User.role` in the codebase are:
